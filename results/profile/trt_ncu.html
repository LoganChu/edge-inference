What the TensorRT kernels are doing

Nsight Compute ran one TensorRT control cycle 31 times, one counter group per run, and read the hardware counters of all 1,742 kernels in vision, the prefix and one denoising step. The other nine denoising steps launch the same kernels, so denoising counts ten times. Times below come from the Nsight Systems trace at normal clocks; the counters explain them.

The TensorRT cycle takes 62.4 ms and keeps the GPU busy for 61.4 ms of it, so it is GPU-bound: kernel time saved comes straight off the cycle. Companion to the full cycle profile of PyTorch eager and TensorRT.

What limits each part of the cycle

Fixable: kernels far below what the GPU can do
  1. 15.9 msper cycle · 26%

    Denoising attention runs on 8 of the 170 SMs latency-bound

    Evidence. _gemm_mha_v2 launches 8 blocks of 128 threads (0.05 waves), so 162 SMs sit idle through each of its 180 calls per cycle. SM throughput is 2.4% and the tensor pipes 2.4% of peak. Only one block fits per SM (8.3% theoretical occupancy, limited by shared memory at 255 registers per thread).

    Cause. The denoiser's 50 action tokens fit in one 64-row query tile, so the kernel launches one block per attention head and each block walks all 1,018 keys (968 prefix tokens plus the 50 action tokens) on its own. The prefix calls the same kernel with 968 queries, gets 128 blocks and reaches 35% SM throughput.

    Fix direction. Split the keys across blocks (split-KV or flash-decoding attention, for example as a TensorRT plugin in the denoise engine). At the prefix call's measured 73 TFLOPS, each call's 0.54 GFLOP would take about 7 µs instead of 108 µs, which puts the ceiling near 15 ms per cycle.

  2. 7.7 msper cycle · 12%

    Vision runs in TF32, at half the tensor-core rate of bf16 compute-bound

    Evidence. Vision's matmuls are sm80_xmma_gemm_f32f32_tf32f32 kernels. The main one runs at 76% of the TF32 tensor peak, and on this GPU the TF32 peak is half of bf16's (about 104 against 207 TFLOPS at ncu's clock).

    Cause. LeRobot keeps vision_tower and multi_modal_projector in fp32 (params_to_keep_float32), so the vision engine was built from fp32 weights and TensorRT runs its matmuls in TF32.

    Fix direction. Build the vision engine with bf16 weights, after checking the actions against the fp32 reference. At the same efficiency the GEMM time roughly halves, about 3.7 ms per cycle.

  3. 3.5 msper cycle · 5.5%

    Time conditioning reads 466 MB of fp32 weights every step memory-bound

    Evidence. One cuBLAS fp32 GEMV per step (gemvx, 14,208 blocks) moves 466 MB at 1.33 TB/s, 76% of DRAM peak. That is about a third of the denoiser's DRAM traffic (466 of 1,355 MB per step).

    Cause. These are the action expert's 37 adaRMS projections (1,024 → 3,072 each, 116.5 M parameters). LeRobot keeps every input_layernorm, post_attention_layernorm and model.norm parameter in fp32, and TensorRT folds the 37 projections into one GEMV. Their only input is the timestep embedding.

    Fix direction. The ten timesteps are fixed (t = 1.0, 0.9, …, 0.1), so compute the scale, shift and gate vectors once per timestep: 10 × 37 × 3,072 fp32 values, 4.5 MB. That removes 4.7 GB of DRAM reads and about 3.4 ms per cycle.

At the hardware limit: only less work or smaller numbers help
  1. 21.8 msper cycle · 35%

    Prefix matmuls run at 74–94% of the bf16 tensor-core peak compute-bound

    Evidence. The main prefill GEMM (64×96 tiles, 18 calls) runs at 189 TFLOPS, 94% of the 207 TFLOPS bf16 peak at ncu's clock, and its warps mostly wait on a full tensor pipe (math-pipe throttle). The 128×128 GEMMs (54 calls) reach 74%; their grids end in a partial wave (4.9 waves), which ncu reports as a tail effect.

    Fix direction. No kernel change recovers much here. FP8 or NVFP4 weights and activations raise the roof itself, which is what this repo's FP8 and NVFP4 engines target.

  2. 6.3 msper cycle · 10%

    Denoising matmuls stream the action expert's weights every step memory-bound

    Evidence. With 50 action tokens, each weight is used 50 times per read. The denoiser's GEMMs move 776 MB per step, 623 MB of it bf16 weights, at 40–60% of DRAM peak, with the tensor pipes at 10–30%.

    Fix direction. Smaller weights: FP8 halves and NVFP4 roughly quarters the 6.2 GB of weights read per cycle. Dropping the 466 MB time-conditioning read also leaves these GEMMs more of the memory bus.

How this was measured

sudo scripts/profile.sh ncu       # ncu, application replay, 9 sections + tensor/DRAM metrics
scripts/profile.sh analyze        # results/profile/profile.json
# report: profiles/ncu/trt_bf16.ncu-repz   (open with /opt/nvidia/nsight-compute/2026.3.1/ncu-ui)
  • Workload: pi05_edge.profile_run --path trt, two warm-up cycles, then one profiled cycle with one denoising step inside cudaProfilerStart/Stop. Each kernel is assigned to the NVTX range (vision, prefix, denoise_step) its launch sits in.
  • Application replay: the program ran 31 times, one counter pass per run, and ncu matched kernels across runs by name and grid. The capture took 3 h 8 min. Kernel replay was not usable: saving and restoring PyTorch's memory pool around every kernel grew ncu past 12 GB of host memory.
  • ncu locks the SM clock at its base, 2,381 MHz, and flushes the caches before every pass, so its kernel times sum to 80.8 ms per cycle against 61.4 ms in the trace (about 2.8 GHz boost). Throughputs are % of peak at ncu's clock: bf16 tensor cores with fp32 accumulation 207.3 TFLOPS, DRAM 1,757.5 GB/s.
  • Tiny kernels look much slower under ncu than in the trace: TensorRT's __myl_Move takes 4.3 µs per call under ncu and 0.6 µs in a normal run. That is why times on this page come from the trace.
  • FLOPs count tensor-core work only (sm__ops_path_tensor_src_*). The SASS fp32 instruction counters read zero on GB202 with this ncu version, so CUDA-core kernels get no roofline point.
