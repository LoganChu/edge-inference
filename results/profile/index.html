Where the control cycle goes: PyTorch eager vs. TensorRT

Nsight Systems traced ten control cycles of each path, with the CUDA API, every kernel and copy, and GPU hardware activity sampled every 20 µs. Nsight Compute then replayed each kernel of vision, the prefix and one denoising step to read its hardware counters (the other nine steps repeat the same kernels). Both paths run the same LIBERO observation and the same noise through the export units in pi05_edge/model.py.

    How this was measured

    • Workload: pi05_edge/profile_run.py. 5 warm-up cycles, then cycles inside a cudaProfilerStart/Stop window with NVTX ranges per stage. Model loading is never captured.
    • Nsight Systems 2026.5.1: CUDA + NVTX + OS runtime trace, 10 cycles per path. A second run per path, as root, adds GPU-metrics sampling at 50 kHz (3 cycles). Every GPU activity is assigned to the stage whose NVTX range contains its launch call.
    • Tracing overhead is small. Traced cycles: . Benchmark medians in results/summary.md: 180 ms eager bf16, 62 ms TensorRT.
    • Nsight Compute 2026.3.1: kernel replay, caches flushed per pass, clocks locked to base. Its durations are therefore longer than the trace's, and its percentages are of the peak at that clock.
    • Raw reports are in profiles/ (git-ignored). The numbers on this page come from results/profile/profile.json, written by pi05_edge/profile_analyze.py.
    scripts/profile.sh trace        # nsys timelines (no special rights)
sudo scripts/profile.sh hw      # nsys GPU metrics + ncu counters (root-only on this box)
scripts/profile.sh analyze      # -> results/profile/profile.json
